Operating

Deployment

The Compose file brings up the application, PostgreSQL, Redis, and a queue worker. It is the whole stack, on any Docker host.

The services

Service What it does
app nginx and PHP-FPM in one runtime image.
db PostgreSQL 18, with a health check the application waits for.
cache Redis 8, used for the cache and the queue.
worker The queue worker. Without it, queued jobs, and with them email, never run.

Bringing it up

git clone https://github.com/lendradev/lightlms.git
cd lightlms
cp .env.example .env

Set at least these before the first start:

APP_ENV=production
APP_DEBUG=false
APP_URL=https://lms.example.edu
DB_CONNECTION=pgsql
DB_HOST=db
DB_PORT=5432
DB_DATABASE=lightlms
DB_USERNAME=lightlms
DB_PASSWORD=<a long password>
REDIS_HOST=cache
QUEUE_CONNECTION=redis
CACHE_STORE=redis
MAIL_MAILER=smtp

Then start the stack and run the migrations:

docker compose up -d
docker compose exec app php artisan migrate --force
docker compose exec app php artisan storage:link

Open the site and the setup wizard walks you through the environment check, the first administrator, and the registration mode.

Storage

The Compose file keeps three volumes: the database, the Redis data, and storage. The storage volume holds uploaded files, the compiled views, and the log files. It is the only one that has to survive a rebuild of the application image.

Updates

git pull
docker compose build
docker compose up -d
docker compose exec app php artisan migrate --force

Backup

The administration area has a one-click backup and restore of the database and the uploaded files. For a server outside the application, back up the db and storage volumes, and keep a copy of .env somewhere safe and private.

Before it goes live

  • APP_DEBUG=false. An error page with a stack trace is a leak.
  • A long random APP_KEY.
  • HTTPS in front of the site. Tokens travel in a header.
  • A queue worker that restarts with the application.
  • Mail configured and tested, or notifications will pile up in the queue.
