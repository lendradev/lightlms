Contributing

LightLMS is a conventional Laravel application. A front-end developer, a PHP developer, and a designer should all be able to read it without a briefing.

The layout

app/
  Enums/          Backed enums for domain values
  Http/Controllers/  Learning/ for learners, Teaching/ for instructors
  Models/         Eloquent models
  Services/       Domain logic that is not tied to HTTP
  Support/        Small shared helpers
bootstrap/app.php  Where the error page and the API errors are registered
database/         Migrations, factories, seeders
resources/
  css/app.css     The design tokens. The only source of colour
  js/components/  shadcn/ui components and the shared shell
  js/pages/       One Inertia page component per route
routes/web.php    All web routes
docs/             Screenshots, the API reference, the engineering notes

The rules that matter

  • Every permission check happens on the server. A hidden button is a convenience, never the control.
  • Quiz answers and marking logic stay on the server. The learner page never receives the correct answer.
  • Controllers stay thin: validate, resolve the course, check the permission, call the service, return a response.
  • Colours come from the tokens in resources/css/app.css. A raw hex value in a component breaks one of the two themes.
  • Every screen has to work in light and dark mode, be keyboard operable, and have an empty, a loading, and an error state.
  • Every behavioural change comes with a test, including the path where the request is refused.

Working on it

corepack enable pnpm
composer install
pnpm install
cp .env.example .env
php artisan key:generate
touch database/database.sqlite
php artisan migrate --seed

Run php artisan serve and pnpm run dev side by side while you work.

Before you open a pull request

php artisan test
composer run lint
pnpm run typecheck
pnpm run lint
pnpm run build

composer run lint reports one known issue in bootstrap/app.php. It is deliberate, and the reason is in docs/engineering-notes.md.

Working with an AI agent

The repository holds an AGENTS.md for coding agents. It maps the codebase, lists the commands that must pass, and records the traps that have cost the project time. Point your agent at it before it writes anything.

docs/engineering-notes.md is worth reading even without an agent. Every entry is a mistake that was made, its cause, and its fix.

Good first changes

  • A forum discussion for a course. The data model is ready for it.
  • A PDF export of the certificate.
  • An Open Badges assertion for a certificate.
  • Course categories in the catalogue.
  • A calendar view of deadlines.
