Integrating

REST API

LightLMS answers on /api/v1 with JSON in and JSON out. Every request needs a bearer token, and the token carries the permissions of the person it belongs to.

Getting a token

A token belongs to one person and acts with that person's permissions. The course-scoped rules of the web apply here too: a token for an instructor in one course gives no access to another course they do not teach.

  1. Sign in to LightLMS.
  2. Open API tokens in the sidebar.
  3. Create a token with a name that says what it is for.

The token is shown once, right after it is created. It cannot be recovered later, only revoked. Revoking it takes effect on the next request. 

Authorization: Bearer <token>

Rate limits

Limit Value
Requests per minute 60
Requests per day 1000

The limit is counted per token, not per address, so one busy integration cannot lock out other people behind the same network. Going over the limit answers with 429 and a Retry-After header.

Response shapes

A single record:

{ "data": { "id": 1, "title": "Systems Thinking for Public Policy" } }

A list of records:

{
  "data": [ { "id": 1 } ],
  "links": { "first": null, "last": null },
  "meta": { "current_page": 1, "last_page": 3, "per_page": 15, "total": 42 }
}

Dates are ISO 8601 in UTC. Marks are numbers, never strings.

Errors

Every failure uses the same body, so a client reads one field instead of parsing prose. 

{
  "error": {
    "code": "validation_failed",
    "message": "The given data was invalid.",
    "details": { "content": ["The content field is required."] }
  }
}
Code Status Meaning
unauthenticated 401 Missing, invalid, or revoked token.
forbidden 403 Valid token, but the person may not do this.
not_found 404 No such record, or none the caller may see.
validation_failed 422 The body did not pass validation.
rate_limited 429 Too many requests.
server_error 500 The server ran into a problem.

A 403 answers a permission question, a 404 answers an existence question. LightLMS answers 404 where 403 would reveal that a record exists but belongs to somebody else.

Endpoints

Base URL: https://your-site.example/api/v1

GET /me

The person the token belongs to.

GET /courses

The published catalogue. Takes q, level, and per_page.

GET /courses/{course}

One course with its modules and activities. The slug identifies the course.

GET /enrollments

The courses the caller is enrolled in, with progress and status.

POST /enrollments

Enrol the caller in a course. The body carries the slug.

{ "course": "systems-thinking-for-public-policy" }

The course must be published and must allow self-enrolment, otherwise the answer is 403.

DELETE /enrollments/{course}

Leave a course. Answers 204.

GET /courses/{course}/participants

The people enrolled in a course. Needs the teaching capability.

GET /courses/{course}/progress/{user}

The progress of one person in one course.

GET /courses/{course}/grades

The gradebook of a course. A learner sees only their own marks; somebody who teaches the course sees every mark.

GET /assignments/{assignment}/submissions

The attempts of the caller on one assignment.

POST /assignments/{assignment}/submissions

Hand in an attempt.

{ "content": "My mapping of the bus route system." }

The content needs at least 10 characters. The attempt limit applies, and a passed deadline without late submission allowed answers 422. Hand-ins through the API are audited like hand-ins through the web.

GET /notifications

The inbox of the caller, newest first.

POST /notifications/{notification}/read

Mark one notification as read.

What the API does not expose

  • Quiz answers, answer keys, and marks before a submission.
  • The contents of a course the caller is not part of.
  • Passwords, tokens, and other secrets of other people.
  • Anything about a person that the caller cannot already see on the web.

Example

TOKEN="1|your-token-here"

curl -s https://your-site.example/api/v1/me \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json"
